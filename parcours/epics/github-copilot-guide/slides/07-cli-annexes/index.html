Copilot CLI : un agent dans le terminal

Le CLI actuel peut explorer un dépôt, modifier des fichiers, lancer des outils et coordonner des sous-agents. Il fonctionne sans VS Code, mais peut aussi s'y connecter. Ce n'est pas l'ancienne extension gh copilot qui suggérait des commandes shell.

Disponibilité générale depuis le 25 février 2026. La dernière entrée du changelog officiel consulté est 1.0.91, datée du 1er octobre 2026. Cette version est plus récente que celle disponible pour vérifier l'aide dans cet environnement.

Repère de version : les commandes ci-dessous sont présentes dans l'aide de Copilot CLI 1.0.82, consultée le 3 octobre 2026. Exécutez /version, /help et /changelog sur votre installation ; une politique d'organisation peut restreindre des fonctionnalités.

Installer et ouvrir un dépôt

# Choisir UNE méthode d'installation
brew install copilot-cli
# ou sous Windows :
winget install GitHub.Copilot
# ou via npm (vérifier les prérequis du paquet officiel) :
npm install -g @github/copilot

cd mon-projet
copilot

Suivez l'authentification proposée, ou utilisez /login. N'insérez jamais un jeton dans une commande partagée ou l'URL d'un remote. Vérifiez vos droits Copilot et ceux du dépôt avant une opération GitHub.

/init écrit ou actualise .github/copilot-instructions.md : ce n'est pas une opération en lecture seule. Relisez les instructions produites. Validez le plan, puis demandez l'implémentation dans le même périmètre. Contrôlez les autorisations, le diff et les tests existants avant un commit.

Ajouts des versions récentes

La référence actuelle documente aussi /sandbox pour l'isolation locale, /goal pour un objectif autonome et /research pour une recherche sourcée. Le sandbox CLI est en public preview, avec des limites selon l'OS et les outils ; il ne confine pas les services MCP distants.

Depuis 1.0.85 (16 septembre 2026), les commandes non interactives copilot skill enable/disable, copilot plugin enable/disable et copilot mcp enable/disable permettent de gérer ces capacités. Ne les supposez pas disponibles sur 1.0.82 : consultez copilot --help et le changelog.

Mode non interactif : une demande depuis le shell

copilot -p "Explique la structure de ce dépôt sans modifier les fichiers."
copilot --help

-p soumet une demande sans ouvrir le même dialogue interactif. Une commande reproductible n'est pas automatiquement sûre : contrôlez les permissions, la sortie et le code de retour avant de l'intégrer à un script ou à une CI. Ne compensez pas un problème d'autorisation en ajoutant aveuglément --allow-all.

CLI et VS Code : deux entrées, des ressources communes

Vous pouvez utiliser le terminal intégré de VS Code, puis /ide pour connecter le CLI au workspace. Le Chat de VS Code conserve son propre sélecteur d'agents et ses commandes ; la connexion ne les transforme pas en commandes CLI.

La connexion peut être automatique lorsque le répertoire correspond à un workspace VS Code de confiance. Une seule instance IDE est connectée à la fois ; sélection, diagnostics et diff peuvent être partagés. Avec --allow-all ou --yolo, les changements sont appliqués directement sans diff d'approbation préalable.

Versionnez les instructions, profils et skills partageables dans le dépôt. Vérifiez leur prise en charge dans chaque client au lieu de supposer que paramètres personnels, permissions ou historique sont automatiquement communs.

Déléguer dans le cloud

/delegate transmet le travail à GitHub afin que l'agent poursuive et propose une pull request. C'est une exécution distante, différente de Fleet local. Vérifiez la branche de base, les accès au dépôt, les politiques et les coûts associés ; une PR proposée n'est ni un merge ni un déploiement.

À éviter pour commencer : /allow-all ou un lancement autorisant tout. Un mode autonome n'est pas un bac à sable. Gardez des confirmations pour les actions sensibles.
