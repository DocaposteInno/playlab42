MCP : connecter Copilot à des outils externes

Model Context Protocol est un protocole ouvert pour relier un assistant à des outils et données. Par exemple : lire un ticket, rechercher une documentation ou interroger un service autorisé, sans coller manuellement son contenu dans chaque prompt.

Un skill décrit une procédure ; MCP fournit des outils et données pour l'appliquer. Ils peuvent se compléter, mais l'un n'installe pas automatiquement l'autre.

Les pièces du système

ComposantRôle
Hôte / clientL'application agent (VS Code, CLI) et sa connexion au serveur.
ServeurExpose des capacités et gère l'accès au service concerné.
ToolsFonctions exécutables, pouvant lire mais aussi modifier des données.
ResourcesSources de contexte proposées par le serveur.
PromptsModèles de demandes exposés par le serveur.
TransportProcessus local (stdio) ou serveur distant HTTP selon le client et le serveur.

Tous les clients et serveurs ne prennent pas en charge les mêmes capacités. Le protocole ne rend pas une intégration automatiquement sûre ou disponible.

MCP dans Copilot, pas les anciennes Extensions

MCP est GA dans VS Code depuis 1.102, publiée le 9 juillet 2025. Les anciennes Copilot Extensions construites comme GitHub Apps ont été retirées le 10 novembre 2025 ; cela ne concerne pas les extensions client VS Code ni les nouveaux plugins agents. Leur configuration n'est pas une référence MCP.

Dans VS Code, configurez les serveurs et sélectionnez les outils nécessaires à l'agent. Dans le CLI, utilisez /mcp ; /env aide à inspecter les capacités chargées. Les politiques d'organisation peuvent restreindre ces usages.

Nouvelle configuration : préférer le format portable

VS Code 1.140 propose .mcp.json à la racine du workspace ou ~/.copilot/mcp-config.json pour l'utilisateur ($COPILOT_HOME/mcp-config.json si défini). Agent Host lit directement ce format.

Exemple de schéma pour un serveur local déjà présent dans votre projet ; le fichier tools/mcp-server.js doit être un vrai serveur MCP, cet exemple ne le crée pas :

{
  "mcpServers": {
    "outil-local": {
      "command": "node",
      "args": ["./tools/mcp-server.js"]
    }
  }
}

Dans le CLI, /mcp permet de gérer les serveurs. Vérifiez les chemins et champs pris en charge par votre version avant d'importer une configuration portable.

Différence de formats : .mcp.json et ~/.copilot/mcp-config.json utilisent mcpServers. L'ancien .vscode/mcp.json utilise servers. Ne changez pas le nom du fichier sans adapter son schéma.

Compatibilité VS Code : exemple GitHub distant

Le format .vscode/mcp.json reste compatible, mais cette destination est dépréciée pour les nouvelles configurations. Avec un harness capable de gérer son authentification, par exemple Local :

{
  "servers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}

Suivez le flux d'authentification du client et la documentation du serveur. Ne placez pas de jeton en clair dans le fichier. Les capacités dépendent des droits de votre compte et des outils activés.

Limite actuelle : la documentation du harness Copilot indique seulement l'accès aux serveurs MCP locaux sans authentification. Ne supposez pas qu'un serveur distant authentifié fonctionnant avec Local fonctionnera aussi avec Copilot. Les configurations VS Code exigeant des entrées interactives ne sont pas transmises à Agent Host.

Premier essai : lire avant d'écrire

  1. Identifiez l'éditeur du serveur, sa maintenance et les données transmises.
  2. Activez le minimum d'outils, idéalement en lecture seule.
  3. Demandez une lecture simple ; inspectez l'appel et la source du résultat.
  4. Gardez une validation humaine pour toute action externe.
Lis le ticket indiqué avec le serveur GitHub autorisé.
Résume le comportement attendu et les critères d'acceptation.
Cite le ticket comme source.
Ne crée aucun commentaire, commit ou pull request.

Une demande en lecture seule dans le prompt ne suffit pas : limitez aussi les permissions des outils et du compte utilisé.

Cas d'usage et précautions

UsagePrécaution
Documentation interneVérifier les droits d'accès et éviter la divulgation dans une session partagée.
Tickets / PRDistinguer lecture, commentaire, création et fusion ; exiger l'accord pour les écritures.
Base de donnéesCompte de lecture seule, environnement d'exercice, aucune donnée personnelle réelle.
Automatisation navigateurPas de session de production ou d'action financière sans supervision.
Serveur stdioRelire la commande et les packages exécutés ; fixer les versions selon la politique du projet.

Les serveurs GitHub, filesystem, bases de données ou documentation sont des exemples de catégories, pas une liste de produits garantis ou approuvés.

Les risques à ne pas oublier

Un serveur local peut exécuter un programme ; un serveur distant peut recevoir vos données. Les réponses d'outils peuvent aussi contenir des injections de prompt. Le protocole MCP ne garantit ni la confidentialité, ni la qualité, ni l'innocuité du serveur.

N'ajoutez pas un connecteur « au cas où » : chaque outil élargit le périmètre accessible à l'agent et peut consommer du contexte.
